# แผนการพัฒนาเพื่อประสิทธิภาพสูงสุด (Best Practices for Performance)

แผนงานนี้จัดทำขึ้นเพื่อเป็นแนวทาง (TODO/Checklist) ในการปรับปรุงแอปพลิเคชันให้อ่านเขียนข้อมูลเร็วขึ้น, ใช้หน่วยความจำ (RAM) น้อยลง, และทำให้ UI ตอบสนองได้ลื่นไหลที่สุด (โดยเฉพาะเมื่อแอปมีข้อมูลการวิ่งจำนวนมาก)

---

## 1. การจัดการข้อมูล (Data Layer & Database)
พาร์ทนี้สำคัญที่สุด เพราะไฟล์ `.fit` หนึ่งไฟล์อาจมีข้อมูล Record นับหมื่นบรรทัด
- [ ] **ใช้ Database Transaction สำหรับการ Insert:**
  - ตอนนำเข้าโหนดข้อมูล (Records) จากไฟล์ `.fit` ให้ใช้คำสั่ง `BEGIN TRANSACTION` และ `COMMIT` ใน SQLite แทนการ `INSERT` ทีละแถวแบบแยกกัน อาจะทำให้เร็วขึ้นกว่าเดิม 10 - 100 เท่า
- [ ] **สร้าง Index สำหรับการค้นหา (Database Indexing):**
  - เพิ่ม `CREATE INDEX idx_records_session_id ON records(session_id);` เพื่อให้การดึงกราฟของแต่ละ Session ไวขึ้น
  - เพิ่ม Index บนคอลัมน์ `started_at` ของตาราง `sessions`
- [ ] **ไม่โหลดข้อมูลทั้งหมดพร้อมกัน (Lazy Loading / Pagination):**
  - ในหน้า **Sessions (รายการวิ่ง)** ให้ดึงมาแค่ `sessions.*` สรุปรวม (ระยะทาง/เวลา) เท่านั้น **อย่าเพิ่งดึง `records`** จนกว่าผู้ใช้จะกดเข้าไปดูกราฟของรอบนั้นๆ

## 2. การสื่อสารระหว่าง Rust Backend <-> JS Frontend (IPC)
- [ ] **ย้ายการวิเคราะห์ไฟล์ .fit ไปไว้ใน Rust (ถ้าเป็นไปได้ในอนาคต):**
  - ตอนนี้เราใช้ `fit-file-parser` ฝั่ง JavaScript ซึ่งแปลว่าเราต้องส่งไฟล์ Binary ก้อนใหญ่ข้ามผ่านสะพาน Tauri IPC ไปให้ JS ถอดรหัส ซึ่งกิน RAM ฝั่ง WebView มหาศาล
  - **Best Practice:** ใช้ Library ของ Rust (เช่น `fitparser` crate) ในการอ่านไฟล์ `.fit` ฝั่ง Backend และคำนวณสรุปค่าต่างๆ แล้วส่งมาแค่รูปแบบ JSON ที่ Frontend ต้องการใช้แสดงผล กราฟ จะทำให้แอปใช้ RAM ลดลงอย่างมาก
- [ ] **เก็บรูปภาพลงโฟลเดอร์ ไม่ใช่ใส่ฐานข้อมูล:**
  - เปลี่ยนจากการแปลงรูปถ่ายน้ำหนักเป็น Base64 แล้วยัดลง SQLite (เพราะจะทำให้ DB บวมและช้ามาก) 
  - **Best Practice:** บันทึกรูปภาพลงไดเรกทอรี่ของระบบ (`appDataDir`) แล้วเก็บแค่ **Path ของรูป** (เช่น `/Users/.../image.jpg`) ลง SQLite จากนั้นใช้คำสั่ง `convertFileSrc` ของ Tauri เพื่อให้ UI นำรูปมาแสดง
